# Qwen3-4B on ANE with a graph sized to each input

English | [中文](zh/06-按输入匹配的ANE固定图.md)

[Article 05](05-qwen3-4b-prefill-decode-energy.md) ended with a question. Its ANE path chose among three fixed graphs, 256 / 2K / 32K, and both speed and energy per token fell away once an input needed the 32K graph. Was that the cost of the graph ladder, or of running a long input on ANE at all? G4 A keeps the weights, inputs and GPU baseline, adapts the same host implementation, and gives each input its own ANE graph.

## 1. The measured work

The six inputs are the same <!-- claim:g4a.contexts@g4a-001 -->500 / 1,024 / 2,048 / 4,096 / 8,192 / 16,384<!-- /claim -->-token documents. Each ANE graph has a capacity just large enough for the input plus 256 decode steps: <!-- claim:g4a.capacities@g4a-002 -->768 / 1,280 / 2,304 / 4,352 / 8,448 / 16,640<!-- /claim --> positions. Each graph keeps only the functions of its own capacity, and the one request per arm that records graph events used no others. The GPU keeps its <!-- claim:g4a.gpu-capacity@g4a-003 -->32,768<!-- /claim -->-position asset.

Each path runs each input in one host session. After a warmup request, the host waits <!-- claim:g4a.quiet@g4a-004 -->25 s<!-- /claim --> idle, runs <!-- claim:g4a.repetitions@g4a-005 -->3<!-- /claim --> requests of <!-- claim:g4a.decode-steps@g4a-006 -->256<!-- /claim --> decode steps from KV N, waits again, then runs a block of one-token prefill requests: <!-- claim:g4a.prefill-counts@g4a-007 -->130 / 90 / 55 / 34 / 15 / 7<!-- /claim --> requests for the six inputs. These counts were fixed from an earlier timing estimate. Inputs run from 16K down to 500, and the first path alternates.

Decode is teacher-forced: every request continues with the same 257 token IDs, taken from an earlier GPU run. At each input size the two paths process the same continuation for the same number of steps. Across input sizes, the continuation stays fixed but attention work grows with KV length. This measures execution, not generation quality. The warmups check that the first and last logits are finite, and at 1K both paths match an independent reference within the recorded thresholds.

Energy is CPU + GPU + ANE software component energy under a <!-- claim:g4a.primary-lag@g4a-008 -->2 s<!-- /claim --> counter lag, without idle subtraction. Each block is admitted on its own: the power stream is complete, the block ends at least <!-- claim:g4a.margin@g4a-009 -->15 s<!-- /claim --> before the last power sample, power responds to the work, and timing coverage holds at 0, 1, 2 and 5 s lags. Decode energy covers first to last token of each request; prefill energy covers the whole block. All <!-- claim:g4a.blocks@g4a-010 -->24<!-- /claim --> blocks passed. Short checks before the run logged direct ANE requests from the host process on every tier and none on the GPU path, and every ANE block shows ANE counter energy. That supports ANE execution; it is not exclusive per-operation placement.

## 2. The GPU is still faster

![Prefill and decode speed at six inputs, with the earlier graph ladder dashed.](../docs/figures/g4a-speed.svg)

The two runs measured decode differently. G3 generated freely for 1024 steps in one request; the comparison uses its first 256 steps, with energy integrated over the same steps, so both cover KV N to N + 255. G3's prefill blocks were timed the same way as these.

At <!-- claim:g4a.n.1024@g4a-011 -->1K<!-- /claim -->, ANE prefill runs at <!-- claim:g4a.prefill.1024.ane-rate@g4a-012 -->887.7 token/s<!-- /claim --> and GPU at <!-- claim:g4a.prefill.1024.gpu-rate@g4a-013 -->3,177.1 token/s<!-- /claim -->; ANE decode from that KV runs at <!-- claim:g4a.decode.1024.ane-rate@g4a-014 -->14.56 token/s<!-- /claim --> and GPU at <!-- claim:g4a.decode.1024.gpu-rate@g4a-015 -->30.09 token/s<!-- /claim -->. Across all six inputs the GPU is <!-- claim:g4a.decode-gpu-faster@g4a-016 -->2.0–3.9×<!-- /claim --> faster in decode and <!-- claim:g4a.prefill-gpu-faster@g4a-017 -->2.9–15.9×<!-- /claim --> faster in prefill. The gap grows because ANE slows more: its decode falls from <!-- claim:g4a.decode.500.ane-rate@g4a-018 -->15.03 token/s<!-- /claim --> to <!-- claim:g4a.decode.16384.ane-rate@g4a-019 -->5.61 token/s<!-- /claim --> over the range, while the GPU's falls from <!-- claim:g4a.decode.500.gpu-rate@g4a-020 -->29.87 token/s<!-- /claim --> to <!-- claim:g4a.decode.16384.gpu-rate@g4a-021 -->21.70 token/s<!-- /claim -->.

## 3. What the graph ladder cost

The dashed curves are G3. Decode that started at <!-- claim:g4a.n.2048@g4a-022 -->2K<!-- /claim --> crossed G3's 2K graph and ran on the 32K graph at <!-- claim:g4a.g3.decode.2048.ane-rate@g4a-023 -->3.11 token/s<!-- /claim -->; with a matched graph it runs at <!-- claim:g4a.decode.2048.ane-rate@g4a-024 -->13.70 token/s<!-- /claim -->, <!-- claim:g4a.vs-g3.decode.2048.speed@g4a-025 -->4.40×<!-- /claim --> faster. Prefill at <!-- claim:g4a.n.4096@g4a-026 -->4K<!-- /claim --> reached G3's 32K graph at <!-- claim:g4a.g3.prefill.4096.ane-rate@g4a-027 -->84.9 token/s<!-- /claim -->; now it runs at <!-- claim:g4a.prefill.4096.ane-rate@g4a-028 -->543.5 token/s<!-- /claim -->. From <!-- claim:g4a.n.2048@g4a-029 -->2K<!-- /claim -->, decode is <!-- claim:g4a.vs-g3.long-decode-speed@g4a-030 -->1.80–4.40×<!-- /claim --> faster and uses <!-- claim:g4a.vs-g3.long-decode-energy@g4a-031 -->0.42–0.68×<!-- /claim --> the energy per token; from <!-- claim:g4a.n.4096@g4a-032 -->4K<!-- /claim -->, prefill is <!-- claim:g4a.vs-g3.long-prefill-speed@g4a-033 -->2.76–6.40×<!-- /claim --> faster and uses <!-- claim:g4a.vs-g3.long-prefill-energy@g4a-034 -->0.42–0.55×<!-- /claim --> the energy.

Where G3 already fitted its 2K graph, little changes: decode at <!-- claim:g4a.n.500@g4a-035 -->500<!-- /claim --> and <!-- claim:g4a.n.1024@g4a-036 -->1K<!-- /claim --> is <!-- claim:g4a.vs-g3.short-decode-speed@g4a-037 -->1.06–1.09×<!-- /claim --> faster, and <!-- claim:g4a.n.2048@g4a-038 -->2K<!-- /claim --> prefill is <!-- claim:g4a.vs-g3.prefill.2048.speed@g4a-039 -->0.94×<!-- /claim --> as fast as G3's 2K prompt graph. The GPU rates of the two runs agree within <!-- claim:g4a.vs-g3.gpu-speed@g4a-040 -->0.97–1.02×<!-- /claim -->, supporting graph capacity as a major explanation. The runs did not match thermal starts and do not isolate other changes on the ANE path.

Matched graphs remove most of the observed long-input penalty; this comparison does not isolate the ladder from every other change between runs. What remains is a slowdown with context that the matched graphs do not remove, and that the GPU does not show to the same degree.

## 4. The GPU holds a work rate; ANE does not

![Implied prefill TFLOP/s and modelled decode read GB/s at six inputs.](../docs/figures/g4a-implied.svg)

These rates combine the measured token rates with the model structure. No device counter or memory traffic was measured, and the byte model excludes padding and current-token writes.

Each prefill token passes <!-- claim:g4a.projection-parameters@g4a-041 -->3.63 billion<!-- /claim --> projection weights, two FLOPs per weight. Adding causal attention over N/2 keys on average, the GPU sustains <!-- claim:g4a.gpu-total-tflops-span@g4a-042 -->20.5–27.2 TFLOP/s<!-- /claim --> across every input: as attention grows, projection work per second shrinks by about as much. ANE falls through <!-- claim:g4a.ane-total-tflops-span@g4a-043 -->1.7–7.0 TFLOP/s<!-- /claim -->. For reference, the same machine's ANE runs a synthetic FP16 convolution chain at about <!-- claim:g4a.synthetic-fp16@g4a-044 -->18.8 T source-equivalent ops/s<!-- /claim --> on one fixed shape.

Decode shows the same split. If every step reads <!-- claim:g4a.weight-bytes@g4a-045 -->8.04 GB<!-- /claim --> of FP16 weights and the existing KV once, the GPU's modelled read rate stays within <!-- claim:g4a.gpu-read-span@g4a-046 -->227–250 GB/s<!-- /claim --> from <!-- claim:g4a.n.500@g4a-047 -->500<!-- /claim --> to <!-- claim:g4a.n.16384@g4a-048 -->16K<!-- /claim -->: fewer tokens per second, but more KV per token. That is what a bandwidth-bound decode would look like, though it does not prove the bottleneck. ANE's modelled rate falls through <!-- claim:g4a.ane-read-span@g4a-049 -->59–122 GB/s<!-- /claim -->.

So on ANE, cost per token grows faster with context than projection work, causal attention or KV reads account for. One candidate is in the graph itself: each decode step evaluates eight query positions, of which one is a real token, so attention over the growing KV is also computed for seven padded positions. Others are attention costing more per FLOP on ANE than the projections, and host work per step. None has been separated.

G6 tested the first candidate. A one-position query does not execute on ANE with this toolchain ([finding](../findings/ane-short-decode-query/)), so the same tiers gained a four-position decode function, which removes four of the seven padded positions without changing capacity. ANE decode ran at <!-- claim:g6.q4-q8-speed@g6-001 -->1.001–1.008×<!-- /claim --> the eight-position speed at every input. This reduction brought little speed benefit, but the compiled work may not shrink in proportion to the logical query width. The cost of padding and the benefit of still narrower queries remain unmeasured.

Total CPU + GPU + ANE energy per token was <!-- claim:g6.q4-q8-components-energy@g6-013 -->0.84–1.02×<!-- /claim --> of Q8 across inputs, so narrowing the query did not lower it at every input.

## 5. Energy

![Component energy per token by CPU, GPU and ANE counter, both paths.](../docs/figures/g4a-energy.svg)

Bars show CPU + GPU + ANE software energy, without idle subtraction. Whiskers describe sample-timing bounds, not sensor accuracy. These are not wall-power measurements. The † marks elevated CPU power relative to neighbouring inputs; the affected blocks are described below.

For <!-- claim:g4a.short-contexts@g4a-050 -->500–2K<!-- /claim --> prefill, ANE spends <!-- claim:g4a.short-prefill-energy-x@g4a-051 -->0.69–0.79×<!-- /claim --> the GPU's energy per input token. At <!-- claim:g4a.long-contexts@g4a-052 -->4K–16K<!-- /claim --> it spends <!-- claim:g4a.long-prefill-energy-x@g4a-053 -->1.05–1.24×<!-- /claim --> as much: the matched graphs pull long-input prefill back to near parity from G3's roughly doubled cost. Decode is <!-- claim:g4a.decode-energy-x@g4a-054 -->0.96–1.18×<!-- /claim -->; removing the CPU counter moves decode to <!-- claim:g4a.decode-energy-x-without-cpu@g4a-055 -->1.07–1.26×<!-- /claim -->, because the ANE path's CPU draw is lower. G6 repeated every arm in new host sessions: repeat speeds are <!-- claim:g6.repeat.speed@g6-002 -->0.97–1.02×<!-- /claim --> those of G4 A, but decode energy per token in the repeat is <!-- claim:g6.repeat.decode-energy@g6-003 -->0.89–1.15×<!-- /claim --> of the first run's. Across both runs <!-- claim:g6.short-contexts@g6-004 -->500–2K<!-- /claim --> prefill stays at <!-- claim:g6.two-run.short-prefill-energy-x@g6-005 -->0.68–0.81×<!-- /claim -->, while <!-- claim:g6.long-contexts@g6-006 -->4K–16K<!-- /claim --> prefill spans <!-- claim:g6.two-run.long-prefill-energy-x@g6-007 -->0.90–1.33×<!-- /claim --> and decode <!-- claim:g6.two-run.decode-energy-x@g6-008 -->0.86–1.18×<!-- /claim -->; these ranges combine input lengths and runs, rather than bounding future variation at a fixed input.

During the ANE path's decode windows, the system GPU counter records <!-- claim:g4a.ane-arm-gpu-decode-energy@g4a-056 -->0.26–0.29 J/token<!-- /claim --> per decode token, <!-- claim:g4a.ane-arm-gpu-decode-share@g4a-057 -->32–58%<!-- /claim --> of the path's decode energy, while the ANE counter records <!-- claim:g4a.ane-arm-ane-decode-energy@g4a-058 -->0.13–0.44 J/token<!-- /claim -->. That counter energy stays nearly constant per token while decode slows almost threefold. It has not been attributed to a process or model operation. Per-token GPU work is one hypothesis; replacing a suspected operation with an equivalent implementation and checking whether GPU-counter energy falls would test that attribution.

Three ANE blocks carry more CPU energy than their neighbours, marked † in the figure. During the ANE <!-- claim:g4a.n.4096@g4a-059 -->4K<!-- /claim --> session the disk was nearly full and diagnostic commands ran: median CPU power was <!-- claim:g4a.decode.4096.ane-cpu-median@g4a-060 -->1.39 W<!-- /claim --> in decode and <!-- claim:g4a.prefill.4096.ane-cpu-median@g4a-061 -->1.17 W<!-- /claim --> in prefill, against <!-- claim:g4a.decode.2048.ane-cpu-median@g4a-062 -->0.77 W<!-- /claim --> and <!-- claim:g4a.prefill.2048.ane-cpu-median@g4a-063 -->0.60 W<!-- /claim --> at <!-- claim:g4a.n.2048@g4a-064 -->2K<!-- /claim -->. Without the CPU counter the ANE <!-- claim:g4a.n.4096@g4a-065 -->4K<!-- /claim --> ratios are <!-- claim:g4a.decode.4096.energy-x-without-cpu@g4a-066 -->1.18×<!-- /claim --> and <!-- claim:g4a.prefill.4096.energy-x-without-cpu@g4a-067 -->0.90×<!-- /claim -->. The ANE <!-- claim:g4a.n.1024@g4a-068 -->1K<!-- /claim --> decode block's median was <!-- claim:g4a.decode.1024.ane-cpu-median@g4a-069 -->1.12 W<!-- /claim -->. These blocks were not rerun.

## 6. Running it: disk space

The run nearly stopped for a reason unrelated to the measurement. On this M5 Pro and macOS build, the tested Qwen3-4B ANE loads left multi-gigabyte compile inputs open in `ANECompilerService` after the loading processes exited. Each ANE host lowered free space by <!-- claim:g4a.disk.per-ane-host@g4a-070 -->6.8–7.0 GiB<!-- /claim --> that did not come back, and the GPU <!-- claim:g4a.n.4096@g4a-071 -->4K<!-- /claim --> load waited at its <!-- claim:g4a.disk.gate@g4a-072 -->30 GiB<!-- /claim --> load gate. Ending the service released <!-- claim:g4a.disk.released@g4a-073 -->189.1 GiB<!-- /claim -->, from files accumulated over two days of ANE work. The wait fell between blocks and the run continued without a restart.

If the same retention occurs with your assets, include it in the disk budget or reclaim it between runs. [The finding](../findings/ane-compiler-service-disk/) has the evidence, and [the workaround](../workarounds/#4-reclaim-disk-space-held-by-the-ane-compiler-service) a task that checks for active measurements before reclaiming.

## 7. What to test next

G6 kept these graphs and changed one thing at a time. The four-position decode query tested section 4's first candidate without isolating compiled padding cost. 4-bit decode weights were not tested on ANE: the upstream iOS 4-bit palettized preset ran entirely on the GPU, at <!-- claim:g6.w4.decode.1024.rate@g6-009 -->2.87 token/s<!-- /claim --> for <!-- claim:g6.n.1024@g6-010 -->1K<!-- /claim --> decode, with FP16 on ANE <!-- claim:g6.w4.fp16-faster-decode@g6-011 -->5.1–8.1×<!-- /claim --> faster, so whether fewer bytes per step help ANE still needs a 4-bit representation that executes there. The GPU-counter energy on the ANE path stays at <!-- claim:g6.decode-gpu-energy@g6-012 -->0.257–0.265 J/token<!-- /claim --> with either query width; attributing it to a process and operation would identify which work to test for removal. A second chip and a quality evaluation are still needed before these curves predict an application.
