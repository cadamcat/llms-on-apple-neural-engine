# ANE 算术兼容性：如何区分舍入差异、scale 错算与模型质量

[English](../03-arithmetic-compatibility.md) | 中文

2026-09-10 · [系列索引](README.md)

**在 ANE 上验证量化模型，首先需要说清楚“相对于什么，结果是正确的”。** 我们的实验遇到过两类很不相同的偏差：一种可以由明确的舍入规则解释，另一种在没有舍入歧义的精确网格输入上仍然出现。把它们都称作“A8 精度损失”，会让修复方向和验收标准一起失去依据。

本文以本仓库的卷积链、QDQ 乘法和分组权重测试为例，说明如何建立可核查的算术参考。新测范围是 M5 Pro、macOS 27.0 build 26A428、Xcode 27.0、coreai-torch 0.4.1 / coreai-core 1.0.0b2 与 coremltools 9.0。历史诊断来自另外的运行，文中单独标记。

## 1. 一个 L2 数字包含了一个参考选择

本文使用的相对 L2 为：

```text
relative_L2(actual, reference) = ||actual − reference||₂ / ||reference||₂
```

它衡量两个张量的相对距离，不是“百分之多少元素错误”，也不是 token 错误率。零参考需要独立检查：本套件要求零输入控制的输出数值为零，而不依赖上述分母。

量化实验至少涉及三种比较。第一种比较量化图的执行结果与该图的算术参考，检查实现是否符合所声明的计算。第二种比较量化结果与 FP16 基线，检查量化过程改变了多少数值。第三种用 NLL、KL 或任务指标评估模型行为。前两种可以帮助解释第三种，但不能代替第三种。

此外，算术参考本身需要明确中间精度和舍入边界。即使写下了同一个矩阵乘公式，使用 FP32 累加后转 FP16、每个分块先转 FP16，或者在中间插入 Q8，得到的都可能是不同的有限精度计算。本仓库的参考实现把这些步骤写在代码中。[参考实现](../../src/ane_scope/references/prepare.py)、[实验方法](../../docs/METHODS.md)

![运行时兼容性、量化结果偏离 FP16 的程度、模型任务质量分别需要不同参考。](../../docs/figures/arithmetic-levels.svg)

## 2. 只改变中点规则，也可能在长链中形成明显差异

考虑对称 Q8、zero point 为 0、scale 为 0.125 的例子。量化前先计算 `x / scale`，然后舍入到整数并限制到 INT8 范围。在恰好位于两个整数中间的位置，两种最近值舍入规则给出不同答案：

| 输入 x | x / scale | 最近偶数 RNE | 中点远离零 RZA |
|---:|---:|---:|---:|
| 0.0625 | 0.5 | 0 | 1 |
| −0.0625 | −0.5 | 0 | −1 |
| 0.1875 | 1.5 | 2 | 2 |

这里的 RZA 指“舍入到最近值，中点选择远离零的一端”，不是向零截断。两种规则都没有增加 INT8 的位宽，也没有改变 scale；差别只发生在中点如何选择。但这个差别若进入下一层卷积和下一次量化，就可能传播到长链的最终输出。

历史首轮 <!-- claim:g1w.qdq.ties-even-mismatches@g1w-001 -->128<!-- /claim --> 层 W8A8 控制对冻结的 RNE 参考出现相对 L2 约 **0.232654**，因此没有进入测速。随后对同一份设备输出做离线诊断：保留 FP16 中间边界，仅调整 Q8 中点规则，RZA 参考的差异约为 **0.000091523**。

**这一步没有改善设备输出，只提出了更能解释输出的算术假设。** 在已经看过输出之后选择参考，还不足以建立新验收标准。原记录仍为失败；后续另外冻结了新输入 seed 20260912、RNE/RZA 两套参考和原有门槛，再执行新输入实验。历史过程和来源哈希见[算术证据摘录](../../results/historical/arithmetic-reference-evidence.json)。

新输入的结果支持了这项解释。当前仓库的[新完整形状记录](../../results/fresh/throughput.json)也保留了两套比较，下面的表格引用这份新测数据：

| 同一 <!-- claim:g1w.qdq.ties-even-mismatches@g1w-002 -->128<!-- /claim --> 层 W8A8 输出 | 相对 L2 |
|---|---:|
| 对事先选择的 Q8 RZA 参考 | 0.000109 |
| 对 Q8 RNE 对照参考 | 0.211 |

这些值来自 Core ML 与 Core AI 新测记录；后者的 A8W4 控制也有相同比较结果。查阅 [`throughput.json`](../../results/fresh/throughput.json) 中各 case 的 `numerical.comparisons` 与 `RNE-not-gate.comparisons`，可以确认比较的是同一输出哈希。RNE 对照只用于比较，不作为准入依据。

这个结果支持的是特定路径上的参考模型。它没有证明 ANE 上所有算术都使用 RZA：本卷积链参考仍保留 FP16 转换的 RNE 边界，SplitConv 的部分和及加法则使用另行冻结的 FP16 RZA 参考。对 RZA 参考仍有 0.000109 的剩余偏差。[方法中的参考边界](../../docs/METHODS.md)

之后的单个 QDQ 探针覆盖了全部输入，而不只是一条链。单位 scale 下输入全部 <!-- claim:g1w.qdq.finite-values@g1w-003 -->63,488<!-- /claim --> 个有限 FP16 值，ANE 上的 Core AI QDQ 与“中点远离零”逐值一致；若按“中点取偶”，其中 <!-- claim:g1w.qdq.ties-even-mismatches@g1w-004 -->128<!-- /claim --> 个值会不同，即 ±0.5、±2.5 这类半整数。[导入的计数](../../results/historical/g1w-e4b-mobile-qat/evidence.json)

## 3. 符合量化参考，仍然可能偏离 FP16 基线

历史新输入实验还比较了 W8A8 和 FP16 的最终输出，两者相对 L2 约为 **0.68**，以 FP16 输出范数为分母。它与“量化输出对自己的 RZA 参考约 0.000109”可以同时成立：一个回答量化图执行得是否符合参考，另一个回答量化图与 FP16 计算相差多少。[来源与分母定义](../../results/historical/arithmetic-reference-evidence.json)

因此，35 T ops/s 正对照的意义是：在已声明的量化语义下，存在通过控制检查的较快执行路径。<!-- claim:g1w.qdq.ties-even-mismatches@g1w-005 -->128<!-- /claim --> 层低熵合成卷积链没有语言任务、attention、KV cache 或词表输出；把其中的 L2 直接解释成语言能力下降比例没有依据。

运行时兼容性门槛和模型质量门槛因此各有用途。更新算术解释不会改变已测的 KL、NLL 或实际 MLP 质量结果；更准确的参考有助于判断下一步该查执行实现还是量化配方。

## 4. 精确网格乘法揭示了另一类问题

为了减少舍入解释的空间，我们使用了一个更小的输入：`g = 2`、`u = 8`，目标输出为 `g × u = 16`。两路输入各经过量化和反量化，即 QDQ，再相乘。

当两路 scale 分别为 0.5 和 2 时，量化前的商都恰好为 4。整数码没有接近饱和边界，也没有处于 0.5 中点；反量化之后应恢复 2 和 8。等 scale 对照使用 2 和 2，商分别为 1 和 4，同样可以精确表示。这些输入不会因为采用 RNE 或 RZA 而产生不同整数码。

新套件在每个配置上执行原输入、零、负输入与重复控制。下面列出原输入结果：

| Core AI 表达 | 两路 scale | 对精确参考的 L2 | 最大绝对差 | 四控制均有 ANE 请求 |
|---|---|---:|---:|---|
| `equal` | 2、2 | 0 | 0 | 是 |
| `unequal` | 0.5、2 | 0.75 | 12 | 是 |
| `reverse_order` | 0.5、2 | 3.0 | 48 | 是 |
| `explicit_q` | 0.5、2 | 0 | 0 | 是 |

`reverse_order` 改变的是两条 QDQ 分支的构造顺序；目标仍是同一个 `g × u`。`explicit_q` 把量化部分写成显式的除法、round、clamp 与整数转换，反量化仍保留。其当前控制通过，说明改变表达可以绕过这个最小例子的错误；它是否适用于更广输入、是否有性能代价，都没有在这里得到验证。[图生成代码](../../src/ane_scope/_coreai.py)、[四组实测](../../results/fresh/smoke.json)

这些结果足以把问题缩小到具体的表达与执行路径。特别是，它们无法由前面的 Q8 中点差异解释。分支构造顺序会改变误差，也值得后续检查编译优化和 scale 处理。现有记录没有内部编译器追踪，尚无法定位是哪一段内部实现造成了这种 scale 与图表达相关的错误。

之后的探针给出了逐值规律。`unequal` 与 `reverse_order` 的输出都是全等数组，记录中的哈希确定其值为 4 和 64；两者都等于两个整数码（均为 4）用同一个分支的 scale 反量化：先构造 `g` 时是 0.5，先构造 `u` 时是 2。另一个无模型探针在全 1 输入上计算 `Q_out(a × Q_1/16(b))`，输出 scale 从 1/16 升到 1/2 时依次返回 1、2、4、8，即 `b` 的整数码用输出 scale 反量化。把乘积裁剪到输出 QDQ 的范围后，各组都恢复为 1。“一个分支用了另一个 QDQ 的 scale”这一替换预测了两个探针中的每个错值，但它仍是从输出推断的。[这项发现](../../findings/coreai-qdq-multiply-scale/)补充了触发它的已发布 QAT 检查点、两种改写各自的边界，以及第二个探针的 Core ML 版本：它在 ANE 上返回同样的值，在 CPU 上返回正确值（2026-09-15 补充）。

ANE 请求只证明这些调用包含 ANE 参与；它没有进一步证明错误发生在具体哪个物理运算单元。历史 0.4.1/0.4.2 隔离对照另存于[版本矩阵](../../results/historical/quantization-expected-results.json)及[来源说明](../../results/historical/quantization-provenance.json)，新套件本轮只运行 0.4.1，未重新比较这两个版本。

## 5. 分组权重测试把误差定位到可检验的 scale 假设

另一个最小例子使用 64 个输出通道、K64、每行两个 K32 scale，以及单位阵输入。单位阵使每个输出值只选中一个权重，避免把长点积的累加误差混入权重解释。

新 Core AI 原生 K64 图中，持久化的四位索引、LUT、二维 scale 和连接关系通过静态审计，但输出有 **1921 / 4096** 个数值与目标不符，相对 L2 为 **0.450247**。设备输出却与另行生成的错误预测一致：把二维 scale 展平后，错误地取前 64 个 scale 当作每行唯一尺度。K32 拆分控制对目标参考的数值差异为零。[控制记录与错误预测比较](../../results/fresh/smoke.json)

我们有一个能够逐值预测错误的具体假设，并有一个正确控制。但“符合错误 scale 展平模型”仍然是观测与解释的对应关系，不等于已经看见内部实现。Core ML 使用另一种直接 INT4 表示，其原生 K64 数值正确但在当前测试中选择 CPU；因此还没有验证该表示在 ANE 上能否正确执行。分组表示和设备选择的完整关系见[第二篇文章](02-分组量化如何改变ANE的执行图.md)。

## 6. 把算术结论写成可复现的证据

读者可以先不使用设备，核对当前发布表格与已有记录：

```sh
.venv/bin/python scripts/summarize.py
.venv/bin/python results/historical/tests/verify_historical.py
.venv/bin/python -m unittest discover -s tests -v
```

第一个命令检查新测表格和已登记的正文数值，第二个检查历史吞吐记录，第三个覆盖舍入中点、饱和及证据损坏等便携检查。它们都不会重新执行 ANE。历史算术摘录另外保留了来源文件、字段和哈希，用于审查原诊断。

在[受支持的本地环境](../../docs/REPRODUCING.md)中，使用新的输出目录运行设备控制：

```sh
.venv/bin/ane-scope run --suite compatibility --output runs/article-arithmetic
.venv/bin/ane-scope verify runs/article-arithmetic
.venv/bin/ane-scope report runs/article-arithmetic
```

该 suite 会执行分组与乘法控制。若要重新获得 <!-- claim:g1w.qdq.ties-even-mismatches@g1w-006 -->128<!-- /claim --> 层的 RNE/RZA 比较，使用 `--suite throughput` 和另一个新输出目录；这是包含完整测速的较重实验。程序会串行执行并应用资源保护。

运行时修复这些行为后，正确输出将作为新观察记录。新实验在运行前冻结参考语义；参考变化时另记版本和验证输入，与原运行分开比较，以区分设备输出、参考解释和模型本身的变化。

后续的 [G2 服务实验](04-W4A16留在ANE上值得吗.md)单独测量 W4A16 的组件速度、热响应和 GPU 共存。
